# Focused sign-in

`/sign-in` now renders SignInForm directly, without AccountShell’s navbar. The public website header, authenticated sidebar and existing password-recovery pages retain their layouts. The sign-in experience uses a centered 440px maximum card, the shared original LOGO artwork, existing Espresso tokens, a Welcome back heading and a minimal Back to website link.

Email and password retain the existing autocomplete semantics. Both are controlled only in component memory, preserving entered values after recoverable failures; passwords are not added to URLs, storage, returned action state or logs. The password starts masked. Eye/EyeOff buttons have accessible names, keyboard focus, pressed state, and preserve selection and pointer focus without delayed focus changes. The surrounding input group and focused eye button each use a single indicator according to which element has focus.

The shared credentials schema retains the original server validation constraints. Local validation focuses the first invalid field, and the server validates again before calling the existing Supabase signInWithPassword provider. Safe credential, network and throttling errors remain inline; no duplicate toast is generated. Client transport failures allow retry while framework navigation signals propagate. Successful sign-in and ordinary authentication callbacks redirect to /dashboard. Existing Dashboard authorization remains enforced: accounts without founder access still follow its POS fallback. Session cookies, roles, protected routes, sign-out and recovery handlers remain in place. The Forgot password link is removed from sign-in; existing direct recovery routes and reset callbacks remain available.

Pending submission locks duplicate submits and uses a local Sign in button state. No artificial delay, client authentication shortcut, provider replacement, new rate limiter or recovery API was introduced. The layout uses min-height: 100dvh, safe padding and natural scrolling on short screens.

Tests cover server validation and provider outcomes using mocks, the Dashboard redirect, five responsive viewports, error/email retention, keyboard submission, password visibility/selection/focus, single indicators, duplicate-submission feedback and a short viewport approximating a mobile keyboard. Production-server tests check the real page, interrupted action transport and protected-route boundaries without sending real credentials. A live successful login still requires an authorized account; none was created or modified for validation.

Validation on November 5, 2026: TypeScript, ESLint and the production build passed. All 23 focused sign-in/receipt browser tests and 30 production-server end-to-end tests passed. The unit run passed 88 tests with the existing Node 26 image-upload stream failure file (`product-image-server.test.ts`) excluded. Desktop, tablet and mobile screenshots were inspected. A short viewport approximates keyboard-reduced space; an actual mobile software keyboard was not exercised.
