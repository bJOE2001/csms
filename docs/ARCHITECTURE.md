# Simple POS architecture

Four product screens: `/pos`, `/menu`, `/app/sales` and `/expenses`; `/app` redirects to Sales. Setup and account recovery support access. Product and category management live exclusively in Menu; operating expense management lives in Expenses.

`src/components/pos/pos-workspace.tsx` owns the cart and one pending sale. `src/components/sales-view.tsx` renders receipts and revenue/profit figures. `expenses-view.tsx` owns expense reporting/search, while `expense-dialog.tsx` owns creation, editing and retained deletion. `src/app/api/pos/route.ts` authenticates, validates bounded requests and calls SQL commands for checkout, products, refunds and expenses. Sales and Expenses both read the existing `pos_expenses` RPC for their applied dates. Shop selection is based on the signed-in user's active membership.

The primary business schema is four tables: `pos_products`, `pos_categories`, `pos_sales` (immutable item/size/price/cost snapshots) and `pos_expenses`, plus the existing identity tables. Expense edits reuse the existing `business_operations` ledger and immutable `audit_logs` infrastructure. Prices and costs are computed in SQL; stable IDs and transaction locks make retries safe. Owners maintain products, expenses and refunds; members can sell and read. Direct table writes are not granted; reads use RLS. New sales are confirmed payments; imported older receipts preserve their historical payment status.

Profit is computed from saved sale costs, never today's product cost. Refunded prepared products retain cost, cancelled sales are excluded, and unknown historical costs prevent a numeric profit figure. Active expenses reduce net profit on their expense date. Voided expenses retain history. The Expenses workspace manages those same records without changing Sales calculations or duplicating storage. Its additive edit RPC checks original values, locks the row, records before/after snapshots and makes retries safe through the existing ledger. Successful writes refresh Expenses and revalidate Sales. The additive profit migration supports old checkout payloads and preserves costs when old clients omit them during editing. Roll back the frontend without dropping additive data. See `EXPENSES_MANAGEMENT.md` for rollout and retention details.

An owner-only `pos_record_cost` command fills a missing receipt cost once, with source note, actor and timestamp on `pos_sales`. A row lock and same-payload replay check prevent conflicting writes. It does not rewrite item snapshots, prices or payment/refund state. It accepts completed/refunded receipts only and rejects overwriting either checkout costs or earlier manual entries. Previous frontends ignore the additive audit columns, so rollback requires no data removal.

Tailwind/shadcn primitives remain under `src/components/ui/primitives/`; semantic colors are in `tokens.css`. The CSS files now cover only current layouts and shared controls. Removed modules, routes, business dispatchers, IndexedDB queue, recipe engine and related tests are deleted, not hidden by navigation.

`WorkspaceShell` composes the four-route navigation with the page content. `workspace-shell.css` owns its full-viewport grid and the POS menu/cart arrangement. Above 760px, Sales, Menu and Expenses scroll in the content pane; POS scrolls its menu and order contents independently. Mobile uses normal document scrolling. `ProductCard` presents size selection and adding to cart, with real category filters and name search. Product management triggers/forms are removed from POS. `MenuWorkspace` and `ExpensesView` reuse the existing dialogs, mutation forms, summary styling and searchable table for owner-only maintenance; members can read both. Optional images use a hosted HTTPS URL or local asset path with an initials fallback. Shared typography uses locally hosted OFL-licensed Manrope, and the existing `Icon` wrapper maps to Lucide React. The white/coral design and control conventions are documented in `docs/UI_DESIGN.md`.

`SaleReceipt` renders the same customer-facing composition in the receipt dialog and printout. `ReceiptDialog` keeps cost records and refund actions outside that composition. `ReceiptPrint` mounts the selected receipt in a body-level portal, so print styles can remove the application and modal overlays without leaving blank pages. It clears the selection after the browser's print dialog closes. Receipt styling lives in `src/app/receipt.css`; no backend or schema changes are needed for presentation.

`ExportSales` downloads a client-generated CSV from the already-authorized Sales props. `src/lib/sales/csv.ts` shares the existing `summarize` function, including per-sale effects of refunds/cancellations, and leaves unknown costs/profits blank with explicit status. It quotes fields, emits UTF-8 BOM/CRLF, preserves exact centavo decimals and neutralizes formula-like user text. No new route, persistence, permission or dependency is needed. Exports cover all loaded records in applied shop dates, not the table's local search results or incomplete date edits. While a new range loads, exports continue to describe the currently loaded report.

`src/lib/sales/period.ts` resolves legacy `?period=today|yesterday|week|month` links using the server's current shop calendar date. Calendar arithmetic uses UTC date-only values to avoid browser timezone and DST shifts; weeks run Monday to today and months run first-day to today. Existing `from`/`to` links remain supported. The shared `DateRangeFilter` automatically navigates after a short pause when both dates are valid and within the existing 366-day SQL limit. It preserves other query parameters, removes a legacy `period` parameter when dates change, and keeps focus and scroll position through client navigation. Incomplete or invalid edits leave the loaded report unchanged. Exports and totals use server-applied dates. Neither page displays shortcut or Apply Dates buttons. Profit margins are part of `summarize`, so screen and CSV share their missing-cost and zero-revenue rules. Date filtering requires no database change.

Historical migrations remain because existing installations have already applied them. The additive upgrade copies menu variants and saved receipts; no historical data is dropped. The hosted migration is not run by the coding agent. Database removal of old history requires an explicit retention and export decision. Pending sales from the retired offline version require reconciliation before deployment.

## Menu and size integrity

Migration `202611020004_menu_management.sql` adds category, description, image URL, sizes and archival fields to the existing product table. A product has zero to twenty sizes in one validated JSON array, each with a stable UUID, custom label, price, direct cost, availability and one default. Atomic product saves avoid a separate variant synchronization API. The legacy regular price/cost mirror the default size for compatible reads; unsized products keep their original price/cost. SQL and Zod validate labels, IDs, monetary limits and defaults. Category deletion is blocked while unarchived products use it; product deletion archives rather than erases.

`useCatalog` shares fetching and focus/storage refresh between Menu and POS. `src/lib/menu/domain.ts` owns catalog schemas and option pricing; `src/lib/pos/cart.ts` owns immutable cart selections. Cart keys combine product and size IDs. A refresh marks changed prices/size labels for explicit review and blocks unavailable or removed selections. The existing SQL checkout verifies current availability, size ID, quoted price and optional quoted size label under product locks, then saves immutable snapshots and selected-size costs. Stable sale IDs retain the prior retry behavior even after menu edits or archival.

All operations stay on `/api/pos` and the existing SQL permission boundary. The optional `size_id`/`size_label` fields extend checkout items; product fields omitted by legacy clients are preserved. No old product names are parsed into invented sizes or categories. Rollout is schema-first; keep the size-aware frontend once sized products are configured. See `MENU_MANAGEMENT.md` for deployment and user guidance.
